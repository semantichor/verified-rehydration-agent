# Anchor Attestation — AGT-VRA-001 / paradigm c

Written after R3.1 integral reading of all 11 buyer-facing files, before R4 paradigm constraint. Answers are the WHAT-anchor of the derivation work.

## Q1. What does the buyer-contract promise as delivered?

The pack delivers a self-contained, normative, execution-neutral agent-logic specification sufficient to build the agent with no further design decisions about agent logic, evidence shape, validator behavior, or failure semantics (`Verified_Rehydration_Agent_README.md`:12). Concretely, the delivered agent-logic surface is: the controlled verdict vocabulary ALLOW / DENY / QUARANTINE / ESCALATE / READMISSION_PENDING (Specification §6), the input/output contracts (§4, §5), the normative verification ordering (§7), failure semantics (§8), the 18-validator catalogue with severity and evidence (§10), decision logic (§11), the S0–S8 workflow and its transition model (§12), gate logic (§13), the evidence contract (§14), and the machine-readable forms (§15); the README frames these as 7 structural properties including that no restoration is permitted before the full verification sequence completes and that any failure triggers fail-safe handling (`Verified_Rehydration_Agent_README.md`:71-72). The Whitepaper positions the same as a pre-operation verification gate that verifies integrity, consistency, freshness, and policy compatibility and otherwise suppresses state into a defined safe mode (Whitepaper §04/§05, guarantees G.01–G.04). These are properties of the specification, not warranties about a running system (`Verified_Rehydration_Agent_README.md`:79).

## Q2. What does the buyer-contract explicitly delegate to deployment?

Five companion deployment artifacts are built by the buyer's engineering team from the specification and are NOT in the pack (`Verified_Rehydration_Agent_README.md`:85-91; Specification §16 Deployment obligations): (1) a stable snapshot facility (snapshot lock or deterministic equivalent with binding evidence); (2) an anti-rollback mechanism (non-regressing counter or equivalent anchor); (3) a local, versioned policy bundle binding policy_id, V_POLICY, and V_COMPAT; (4) a single-writer persistence control plane emitting writer-lock and contention evidence; and (5) a readmission authority workflow (approver_set, recovery workflow, readmission-token evidence, release procedure). I do not implement these; they are deployment substrate.

## Q3. How does the conformance test suite partition?

The suite is 29 records anchored 1:1 to the specification (`Verified_Rehydration_Agent_README.md`:99): 26 directly runnable on the agent's projection surface, 1 parameterized against operator-declared inputs (PT-024, authority-release branch), and 2 declarative checks verified at integration level (PT-028 for V_COMPAT, PT-029 for V_WRITER_LOCK) (`Verified_Rehydration_Agent_Conformance_Tests.md`:14-45, §4 Minimal Run Note:508-518).

## Q4. Where is the boundary between spec-derivable and deployment-substrate PTs?

The 26 runnable records plus the parameterized PT-024 exercise the locally derivable projection surface the Minimal Run Note names — a workflow transition surface equivalent to next_state(current_state, trigger, validator_passed) and an evidence surface emitting the principal bundle fields and producer tags (`Verified_Rehydration_Agent_Conformance_Tests.md`:510-514) — and are spec-derivable and locally runnable. The boundary falls at the two declarative records PT-028 (V_COMPAT) and PT-029 (V_WRITER_LOCK): the Minimal Run Note designates these as bounded external obligations not locally runnable, proved by architecture evidence rather than the local transition surface, because they depend on deployment-substrate values (policy-compatibility enforcement subsystem, persistence control plane) the pack delegates to deployment (`Verified_Rehydration_Agent_Conformance_Tests.md`:518; `Verified_Rehydration_Agent_README.md`:85-91). These two are the only legitimate SKIPs.
